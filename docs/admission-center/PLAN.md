## 2. 지난 연결 시도가 안착하지 못한 이유 (확인된 사실)

### (1) 14개 중 2개만 들어왔고, 나머지는 새 탭이었습니다

`GradeCenter.js`(53KB)가 흡수한 것은 **성적 진단 + 수시 시뮬레이터 표**뿐입니다. 나머지는 전부

```js
export function openStudio(page) {
  window.open(`/grade/${page}.html`, '_blank', 'noopener');
}
```

즉 정시·전문대·모의고사·생기부·탐구주제·과목설계·리포트·OMR·등급컷·성취도는 **여전히 별도 HTML**이고, 화면에는 사이드바가 두 개(React 사이드바 + grade 사이드바) 생깁니다.

### (2) 두 화면을 잇는 다리가 `localStorage` 였습니다

`bridge.js` → `localStorage['mimperial.students.v1']`. 여기서 파생되는 문제가 전부입니다.

| 문제 | 구체적으로 |
|---|---|
| PC마다 데이터가 다름 | 원장 PC / 상담실 노트북 / 조교 PC가 서로 다른 학생 명부를 가짐. 동기화 수단이 **JSON 파일 수동 이동**뿐 |
| 학생 명부가 둘 | 시스템은 `users`, 스튜디오는 `mimperial.students`. `bridge.js`가 `systemId` → `이름+학교` 순으로 봉합을 시도하지만, 폴백 단계에서 **같은 학교 동명이인이 한 레코드로 합쳐질 수 있음** (코드 주석도 이 위험을 인지하고 2패스로 방어) |
| 인증이 없음 | `/grade/*.html` 은 정적 파일입니다. Firestore 규칙이 걸리지 않으므로 **URL을 아는 사람은 로그인 없이 열고 입력할 수 있습니다.** 학원 시스템 본체와 보안 수준이 다릅니다 |
| 상담 흐름이 끊김 | 새 탭 + 학생 전환 시 `location.reload()`. 상담 중 화면을 오가면 매번 리로드 |
| 용량 한계 | 저장 실패 시 `alert('저장 공간이 부족...')` 경로가 실제로 코드에 있습니다 |

### (3) 경로가 `/grade/` 안에서만 성립합니다

원본 페이지들은 `fetch('data/admissions.json')` 처럼 **상대경로**를 씁니다. SPA 라우트에서는 깨집니다. 지난 시도의 `lib/data-loader.js`가 절대경로로 바꿔 둔 것이 바로 그 증거입니다 — 나머지 화면을 옮기면 같은 수정을 12번 더 해야 합니다.

### (4) AI 기능 2개는 로컬 Node 서버 전용입니다

| 기능 | 호출 | 배포 환경에서 |
|---|---|---|
| 탐구 주제 실시간 생성 | `fetch('api/topics')`, `api/health` | Cloudflare Pages에서 **404** |
| AI 면접 예상 질문 | `fetch('api/interview')` | 동일 |

grade는 `시작.bat`으로 띄우는 자체 서버를 전제로 만들어졌습니다. 참고로 **수시 6장 조합 추천은 규칙 기반**이라 서버가 필요 없습니다(오해하기 쉬운 지점).

### (5) 입시 자료가 두 벌로 갈려 있습니다 — 이게 가장 중요합니다

| | 입시 내비게이터 (현재 가동 중) | grade 시뮬레이터 |
|---|---|---|
| 파일 | `public/data/admissions_data.json` (1.5MB) | `grade/data/admissions.json` (4.6MB) |
| 형태 | `{region, univ, type, dept, cut, min, max}` 평면 배열 | 컬럼형 + 문자열 사전, 28,649행 |
| 담긴 것 | 컷 3개 값만 | 컷(5등급 환산) · 수능최저 438종 구조화 · 고사일정 · 지역인재 2,763건 · 여대 여부 · 9대 계열 분류 |
| 산출 근거 | `make_data.py`의 '2028 예측 컷' 컬럼 (블랙박스) | `predict.mjs` — 원시 연도별 컷에서 직접 산출, 역검증 MAE 0.440 기록 있음 |

**같은 대학·같은 학과를 두 화면이 다르게 판정합니다.**

여기서 별도로 확인된 것 하나 — 입시 내비게이터는 내신 평균을 `calc5Grade`(1~5등급)로 만들어 `admissions_data.json`의 `cut`과 비교합니다. 그런데 그 `cut` 값들은 9등급대 분포로 보입니다(예: 가야대 간호 1.98, 사회복지상담 4.35). **척도가 엇갈린 채 판정하고 있을 가능성이 있습니다.** grade 엔진이 명시적으로 해결해 둔 문제와 정확히 같은 것이며, 통합의 부수 효과로 고쳐집니다. 이건 통합과 무관하게 따로 검증할 값이 있습니다.

## 4. 구상 — 세 층으로 갈라서 봅니다

핵심 판단은 하나입니다.

> **"스튜디오로 보내기"를 버립니다.** 엔진과 자료만 가져오고, 화면과 저장은 기존 시스템의 방식(React + Tailwind + Firestore)으로 다시 얹습니다.

| 층 | 무엇 | 재작성 |
|---|---|---|
| **엔진** (계산) | `shared/*.mjs` 19개 + `core/{data,exams,achieve}.js` | **0** (fetch 경로만 절대경로로) |
| **자료** (요강) | JSON 14개 | **0** (위치만 이동) |
| **화면·저장** | HTML 14개 + `store.js` + `app.css` | **전부** ← 작업량의 95% |

`shared/students.mjs`는 **버립니다.** 학생 문서 모델이 Firestore로 대체되므로 존재 이유가 사라집니다(필드 정규화 로직만 스키마 검증으로 흡수).

`grade-import.js`(buildStudentPatch)는 **그대로 살립니다.** `grades` 컬렉션 → 5등급 환산 변환기이고, 이미 테스트 파일까지 있으며 검증된 코드입니다. 이것이 "성적을 두 번 입력하지 않는다"를 성립시키는 유일한 부품입니다.

## 5. 사이드바 안착 구조

현재 사이드바는 5그룹 30개입니다. 여기에 14개를 더 넣으면 메뉴가 무너집니다. **메뉴 1개 + 내부 탭**이 맞습니다.

기존 `학습 및 수강` 그룹의 [입시 내비게이터] 바로 아래:

```
학습 및 수강
  …
  입시 내비게이터   /navigator    학생·학부모도 봄 — 그대로 유지
  입시 전략 센터    /admission    교직원 전용 (신규)   ← 14개가 여기 들어갑니다
```

`/admission` 내부는 **상담 흐름 순서**의 탭 5개 — grade 자체 사이드바의 5그룹을 그대로 계승합니다(그쪽 주석도 "실제 상담 흐름을 그대로 따른다"고 적고 있습니다).

| 탭 | 흡수 | 비고 |
|---|---|---|
| 진단 브리핑 | `index` | D-Day · 다음 할 일 · 마스터플랜 |
| 성적 · 프로필 | `score` `mock` `converter` `exam-admin` | 내신은 `grades`에서 자동, 사람은 **보정만** 입력 |
| 수시 · 정시 | `simulator` `jungsi` `college` | 서브탭 3개 |
| 학생부종합 | `record` `topics` `curriculum` | |
| 종합 리포트 | `report` | 인쇄 전용 |

**학생 선택은 URL로 합니다** — `/admission/:studentId/simulator`. `/navigator/:studentId`가 이미 같은 규약을 씁니다. 이것만으로 세 가지가 해결됩니다.

- 상담 중 URL을 복사해 동료에게 넘길 수 있습니다
- 새로고침해도 학생이 유지됩니다 → "활성 학생" 개념과 `location.reload()`가 전부 불필요해집니다
- 사이드바 상단의 학생 전환 카드도 필요 없어집니다 (기존 시스템의 학생 검색을 그대로 씁니다)

**`students` 화면과 `omr`은 넣지 않습니다.**
- `students`(학생 목록·백업·복원)는 `users` + `UserManager`가 이미 하는 일입니다. 명부를 두 개 만들면 지난 실패를 이름만 바꿔 되풀이합니다.
- `omr`(OMR 채점)은 `시험 진단 입력`이 하는 일입니다. 지금 붙이면 채점 경로가 둘로 갈립니다. **별건으로 분리**해서 시험 진단 쪽 과제로 넘깁니다.

## 6. 저장 계층 — localStorage를 Firestore로

컬렉션 3개를 새로 만듭니다. 경로 규약은 기존과 같습니다(`artifacts/{APP_ID}/public/data/…`).

### `admission_profiles/{studentId}` — **문서 ID = users 문서 ID**

이 한 줄이 지난 실패의 절반을 없앱니다. `systemId` 매칭도, 이름+학교 폴백도, 동명이인 위험도 전부 사라집니다.

담는 것은 **시스템에 없는 것만**입니다.

| 필드 | 왜 필요한가 |
|---|---|
| `gender` `hsType` `studentZone` `recordQuality` | `users`에 없음. 여대 필터·지역인재·고교유형 보정에 필수 |
| `scoreAll/Soc/Sci` (보정값) | 상담사의 명시적 판단. 자동 산출값보다 우선 |
| `achieveSheet` | 성취도 A·B·C 과목 — `grades`는 등급만 받으므로 시스템에 아예 없음 |
| `mockDetail` | 표준점수·백분위 원자료. `grades`에는 등급만 있어 정시 환산이 불가능 |
| `cart` `collegeCart` `picks` | 원서 후보와 6장 확정 |
| `recordResult` `interviewPrep` | 생기부 진단 요약 (재분석 방지) |

**절대 복제하지 않는 것**: `name` `school` `grade` → `users`에서 읽습니다. 내신 원본 → `grades`에서 매번 `buildStudentPatch`로 파생합니다. 복제하면 반드시 어긋납니다.

### `admission_exams/{examId}` · `admission_achieve_policies/{docId}`

학생과 무관한 **자료 자산**입니다(등급컷 등록본, 대학별 성취도 정책). 원장·행정만 쓰기, 교직원 읽기.

### 규칙 초안

```
match /admission_profiles/{studentId} {
  allow read:  if isStaff(appId) || isMineOrChild(appId, studentId);
  allow write: if isDesk(appId);
}
match /admission_exams/{docId}            { allow read: if isStaff(appId); allow write: if isDesk(appId); }
match /admission_achieve_policies/{docId} { allow read: if isStaff(appId); allow write: if isDesk(appId); }
```

`docs/HANDOFF.md`의 배포 순서 규약을 따릅니다 — **규칙을 넓히므로 규칙 먼저, 앱 나중.** `tests/rules.test.mjs`에 케이스 추가(현재 89건).

> `read`에 학생·학부모를 포함할지는 **결정이 필요합니다**(아래 9절). 지금은 포함한 초안이지만, 상담용 판정("위험", "합격 확률 12%")을 학부모가 직접 보는 것이 옳은지는 별개 문제입니다.

## 7. 입시 내비게이터 ↔ 진로진학 상담 연결

요청의 핵심입니다. 지금 끊긴 지점이 셋입니다.

### (1) 자료를 하나로

입시 내비게이터가 읽는 곳을 새 데이터셋으로 옮깁니다. **옛 파일은 남겨 두고 읽는 쪽만 바꿉니다**(한 줄 되돌리면 원복). 그러면 네비게이터도 수능 최저·고사일정·지역인재를 갖게 되고, 2절에서 지적한 척도 엇갈림이 함께 해소됩니다.

### (2) 상담 기록을 하나로

grade는 상담 이력을 학생 문서 안 `notes[]`에 넣었습니다. 시스템에는 이미 `consultations`(예약)와 `consult_history`가 있습니다.

→ 진로진학 상담을 **`consult_history`에 `kind:'admission'`** 으로 넣습니다. 그러면 한 줄로 이어집니다.

```
신규 상담 등록(ConsultationManager)
      ↓  입회
입시 내비게이터 — 성적 입력 · 목표 대학
      ↓  같은 학생 · 같은 성적
입시 전략 센터 — 수시/정시 판정 · 원서 6장 · 생기부
      ↓
종합 리포트 → 상담 기록(consult_history) → 다음 상담 예정일
```

부수 효과: `report`의 "최근 상담 이력" 카드가 **실제 학원 상담 기록**을 읽습니다(지금은 별도 localStorage라 학원 기록과 무관).

### (3) 리포트에 착지점을 줍니다

`report`는 학부모 면담용 인쇄물입니다. 실제 상담 산출물이 되려면 나가는 길이 있어야 합니다.

- 1단계: 인쇄만 (지금과 동일)
- 2단계: `utils/driveLink.js`(이미 있음)로 PDF 보관, 또는 `통합 메시지 센터`로 요약 발송 (`sms_outbox` 경로 이미 있음)

### AI 2개는 Functions로

`functions/index.js`에 이미 Gemini가 붙어 있습니다(`refineFeedback`, `analyzeExamPaper`, `parseReportCard`). 같은 패턴으로 `onCall` 2개를 추가합니다.

**단, NDJSON 스트리밍 진행 표시는 포기합니다.** `onCall`은 스트리밍이 안 됩니다. 주제 5개 생성이 20~40초라 스피너로 견딜 수 있는 범위입니다. 스트리밍이 꼭 필요하면 `onRequest` + SSE지만 인증을 직접 처리해야 해서 1단계 밖입니다. **이 둘 없이도 주제 DB 검색과 PDF 생기부 진단은 동작합니다** — grade도 그렇게 설계돼 있습니다.

## 9. 예상 결과 — 얻는 것과 대가

### 얻는 것

- 28,649개 전형 · 수능최저 438종 · 고사일정 · 지역인재 판정이 **학원 시스템 안에서** 동작
- **성적 재입력 0회** — `grades` → 자동 환산 (변환기가 이미 검증됨)
- 신규 상담 → 진로진학 상담 → 리포트가 **한 줄**
- 어느 PC에서든 같은 데이터 · 파일 수동 이동 소멸
- 인증 없는 `/grade/*.html` 경로가 사라짐
- 학생·학부모에게 자기 진단을 (읽기 전용으로) 열 수 있는 길이 열림 — localStorage로는 원천 불가능했던 것

### 대가

| 항목 | 실제 크기 |
|---|---|
| **작업량** | 화면 재작성이 실질 전부. 화면 JS 약 4,600행 + 코어 1,400행 + HTML 약 200KB. 큰 덩어리는 `simulator` 965행 · `topics` 651행 · `jungsi` 519행. 화면당 반나절~하루, **전체 2~3주**(기존 유지보수 병행 시) |
| **정적 자산 10.4MB** | 저장소는 `public/`만 한 번 커집니다(`build/`는 gitignore). 런타임은 화면 진입 시 lazy fetch라 첫 로딩에 영향 없음 |
| **첫 진입 지연** | `admissions.json` 4.6MB 파싱 — 상담용 노트북에서 1~3초. gzip 전송 0.6MB, 모듈 캐시라 두 번째부터 즉시. (구 버전은 8.5MB 엑셀을 브라우저에서 파싱했습니다 — 이미 크게 줄여 온 상태) |
| **잃는 것** | AI 생성 진행 표시(NDJSON) · grade 자체 디자인(`app.css` 20KB → Tailwind로 다시) |

### 가장 큰 위험 — 자료가 이미 **한 학년도 뒤처져 있습니다**

`meta.json` 기준:

```
admissionYear : 2026
builtAt       : 2026-08-05
원본          : 목동임페리얼학원_2028_5등급제_통계정밀보정.xlsx, 전국 대학 구분.xlsx
```

지금 상담하는 고3은 **2027학년도** 지원자이고, 수시 원서 접수는 **2026-09-09**입니다. grade 앱 스스로도 `setDataYear()`로 "지난 자료"라고 표시하도록 만들어져 있습니다(`ui.js:287`).

그리고 **JSON을 다시 굽는 Node 빌드 스크립트를 찾지 못했습니다.**

- 원본 엑셀 3개는 `F:\grade`에 있습니다 (8.5MB · 8.9MB · 6.6MB)
- `F:\grade\make_data.py`는 **구버전** 파이프라인입니다 (새 엔진이 "블랙박스"라고 지적한 그것)
- 새 파이프라인이 참조하는 `build/build-curriculum.mjs`, `build/extract-legacy.mjs`, `server.js`, `시작.bat`은 F: 드라이브 3단계 깊이까지 탐색해도 없었습니다

**이것이 확인되지 않으면, 통합을 마친 뒤에도 자료가 2026학년도에 굳습니다.** 통합보다 먼저 확인할 일입니다.

## 11. 원장 확인이 필요한 것

1. **`admissions.json` 재생성 경로** — 2027학년도 요강을 어떻게 다시 굽습니까? 새 빌드 스크립트가 어디에 있습니까? (없다면 통합 착수 전에 이것부터 복원해야 합니다)

4. **`전문대 진단`(colleges.json 2.2MB)을 1차에 포함할지** — 빼면 정적 자산이 8.2MB로 줄어듭니다
