# 시험 진단 입력 — 재설계 계획

> 작성: 2026-08-11 · 대상 화면 `src/features/ExamDiagnosticInput.js`
> 근거: 6축 병렬 감사 + 적대적 반증 (생존 80건 / 반증 6건, 치명 11 · 높음 24)

---

## 0. 지금 상태 요약

한 줄로: **이 화면은 채점에 쓸 수 없고, 저장된 데이터는 학생·학부모에게 도달하지 않습니다.**

세 겹의 문제가 겹쳐 있어 하나만 고쳐도 다음 것이 드러납니다.

```
① 입력 불가   반 학생 명단이 항상 비어 있음        → 채점 자체가 시작 안 됨
② 점수 오염   만점 100 고정 + 배점 0 폴백 실패     → 저장돼도 숫자가 틀림
③ 도달 실패   examDocId 미저장 + 이름으로 조회      → 맞아도 화면에 안 나옴
```

`examDocId` 를 고치는 순간 ②에서 잘못 쌓인 점수가 **한꺼번에 학부모에게 노출**됩니다.
그래서 순서가 중요합니다. ③을 먼저 고치면 안 됩니다.

## 2. 재설계 — 두 개의 점수

### 왜 두 개인가

원장 요구: 표면 점수 하나로는 실력을 못 본다. 찍어서 맞은 것을 걷어낸 점수가 필요하다.

**두 숫자를 따로 타이핑하게 하지 않습니다.** 문항별 판정 한 번으로 둘 다 나옵니다.

| 판정 | 뜻 | 표면 | 실질 |
|---|---|:---:|:---:|
| `solid` | 맞았고 풀이도 정당 | ○ | ○ |
| `lucky` | 맞았지만 찍었거나 논리에 구멍 | ○ | ✕ |
| `wrong` | 틀림 | ✕ | ✕ |
| `blank` | 무응답 | ✕ | ✕ |

```
표면 점수 = Σ 배점(solid + lucky)
실질 점수 = Σ 배점(solid)
거품      = 표면 − 실질
```

거품이 핵심 지표입니다. **88/72 인 학생과 75/73 인 학생은 완전히 다른 처방이 필요합니다.**
앞은 운으로 버티는 중이고 뒤는 실력이 점수와 일치합니다.
표면 점수만 보면 앞 학생이 더 잘하는 것처럼 보입니다.

빠른 입력이 필요하면 두 숫자 직접 입력도 허용하되, `scoring.method` 로 구분해 기록합니다.

### 2단계 워크플로우 — 조교와 강사의 분업

실질 점수는 **풀이를 읽어야** 판정할 수 있습니다. 답안지 대조만으로는 불가능합니다.
그래서 작업이 원래 두 단계로 나뉩니다.

```
1차 채점 (조교)   답안지 대조 → wrong / blank 표시     → 표면 점수 확정
                  이 시점의 정답은 전부 잠정 solid
                         ↓  stage: scored
2차 검토 (강사)   맞은 문항의 풀이를 읽고 lucky 로 강등  → 실질 점수 확정
                         ↓  stage: reviewed
```

**중요:** `stage: scored` 단계에서는 실질 점수 = 표면 점수입니다.
이때 실질 점수를 학부모에게 보여주면 거짓말이 됩니다.
`reviewed` 가 되기 전에는 화면에 "검토 대기"로 표시하고 숫자를 감춥니다.

클리닉 피드백의 "저장 및 검수 요청" 과 같은 패턴이라 조교에게 익숙합니다.

### 조교 권한

- Firestore 규칙: `STAFF()` 에 `ta` 가 이미 포함돼 있습니다 (`firestore.rules:83`). **변경 불필요.**
- 화면 라우트: `App.js:665` 가 `['admin','lecturer','admin_assistant']` 로 막고 있습니다. **`ta` 추가 필요.**
- 조교는 1차 채점만, 2차 검토(lucky 판정)는 강사·원장만 — 화면에서 구분합니다.

## 3. 데이터 스키마 v2

```yaml
# artifacts/{APP_ID}/public/data/student_exam_diagnostics/{docId}
schemaVersion: 2

# ── 시험 식별 ──────────────────────────────────
kind: school | concept | mock
examDocId: "2026_목동고_2학년_1학기_중간고사_수학"   # school 일 때만. 나머지는 없음(정상)
examTitle: "[개념테스트] 7월 4주차 주간평가"          # 항상 있음. 화면 표시는 이걸로
unitName: "함수의 극한과 연속"
subject: "수학"

# ── 학생 ──────────────────────────────────────
studentId: "abc123"        # ← 유일한 조회 키. 이름으로 조회하지 않는다
studentName: "홍길동"       # 표시용 사본. 이름이 바뀌어도 기록은 안 끊긴다

# ── 점수 ──────────────────────────────────────
maxScore: 80               # 만점 명시. 100 고정 폐기
surfaceScore: 64           # 표면 점수
trueScore: 52              # 실질 점수
bubble: 12                 # surfaceScore - trueScore. 질의용으로 저장

# ── 문항별 (미래 분석의 씨앗) ────────────────────
responses:
  - { no: "3",  points: 4, verdict: solid }
  - { no: "7",  points: 4, verdict: lucky }
  - { no: "12", points: 5, verdict: wrong }
  - { no: "23", points: 6, verdict: blank }

# ── 진행 상태 ──────────────────────────────────
scoring:
  method: per_question | manual
  stage:  scored | reviewed
  scoredBy:   { uid: "...", name: "김조교", at: <ts> }
  reviewedBy: { uid: "...", name: "박강사", at: <ts> }

instructorComment: ""
growthPlan: ""
createdAt / updatedAt
```

### 지금 안 넣지만 자리를 비워두는 것

`responses[]` 항목에 나중에 필드를 더해도 기존 기록은 그대로 동작합니다.

```yaml
  - no: "12"
    points: 5
    verdict: wrong
    # ↓ 2차 개발에서 추가. 없어도 지금 동작함
    conceptIds: ["ANA-07-03-05"]        # AI 수학 지식 맵 연결
    errorType: 계산실수 | 개념부재 | 문제해석 | 시간부족
    timeSpent: 210                       # 초
```

**이 `responses[]` 배열 하나가 미래 분석 전체의 전제조건입니다.**
지금 `wrongQuestionNumbers: ['3','7']` 만 저장하면 나중에 문항별 데이터를 붙일 자리가 없습니다.

## 4. 문항별 데이터로 열리는 것

`responses[]` 가 쌓이면 아래가 **추가 입력 없이** 계산됩니다.

| 분석 | 필요 조건 | 누구에게 쓸모 |
|---|---|---|
| 문항별 정답률 | 같은 `examDocId` 기록 여러 건 | 강사 — 다음 수업에서 다룰 문항 우선순위 |
| 거품률 순위 | `bubble / maxScore` | 원장 — 점수는 높은데 위험한 학생 조기 발견 |
| 오답 상위 문항 | `verdict == wrong` 집계 | 강사 — 반 전체 공통 취약점 |
| 찍맞 상위 문항 | `verdict == lucky` 집계 | 강사 — 학생들이 원리 없이 넘어간 문항 |
| 학생별 추이 | `studentId` + `createdAt` | 학부모 상담 — 실질 점수 추이가 진짜 성장 곡선 |
| 취약 개념 → 클리닉 과제 | `conceptIds` (2차) | 조교 — 클리닉 과제 자동 생성 |

### 집계는 클라이언트가 하지 않습니다

`exam_stats/{examDocId}` 집계 문서를 **Cloud Functions `onWrite`** 로 만듭니다.

- 클라이언트가 반 전체 기록을 읽으면 문서 읽기 비용이 학생 수만큼 곱해집니다
- 같은 계산식이 화면마다 복제되면 서로 다른 숫자가 나옵니다 (온톨로지에서 겪은 문제와 동일)

## 5. 작업 순서

각 단계는 앞 단계 없이는 검증할 수 없습니다.

| 단계 | 작업 | 왜 이 순서인가 |
|---|---|---|
| **0** | 반 학생 명단을 `enrollments` 기준으로 복구 | 이게 없으면 아무것도 시험할 수 없다 |
| **1** | 만점 명시(`maxScore`) + 배점 0 폴백 수정 | 새 데이터가 오염되는 것부터 멈춘다 |
| **2** | 탭 전환 시 입력 유실 방지 (확인창 + 탭별 보관) | 강사가 30명분을 잃지 않게 |
| **3** | 스키마 v2 — 두 점수 + `responses[]` + `examDocId` | 데이터 모양을 확정 |
| **4** | 조교 라우트 개방 + 2단계 워크플로우(`stage`) | 분업 시작 |
| **5** | 수정·삭제 UI (현재 0곳) | 잘못 저장된 것을 고칠 수단 |
| **6** | 소비자 화면 복구 — `studentId` 조회, 학부모 자녀 선택 | 여기서 비로소 학생·학부모에게 도달 |
| **7** | `concept_stats` 쓰기를 유니버스 읽기 모양에 맞춤 | 유니버스 고정값 제거 |
| **8** | `exam_stats` 집계 Functions + 분석 화면 | 문항별 분석 개시 |

**6단계를 1·3단계보다 먼저 하면 안 됩니다.** 지금 DB 에 쌓인 잘못된 100점들이
그 순간 학생·학부모 화면에 한꺼번에 드러납니다.

### 기존 데이터 처리

2026-07-23 이후 이 화면으로 저장된 기록은 `examDocId` 가 없고 점수가 100 고정일 수 있습니다.
6단계 전에 **점검 스크립트로 전수 조회 → 원장 확인 → 일괄 정정 또는 숨김** 이 필요합니다.
`schemaVersion` 이 없는 기록은 화면에서 "재채점 필요"로 표시하는 것이 가장 안전합니다.

## 6. 미결 — 원장 확인 필요

1. **점수 저장 방식** — 원점수(64/80) 저장인가, 백분율(80.0) 환산 저장인가?
   내신은 원점수, 개념테스트는 백분율이 자연스러운데 섞으면 추이 차트가 깨집니다.
2. **`lucky` 판정 권한** — 조교도 할 수 있게 할 것인가, 강사·원장만인가?
3. **학부모 노출 범위** — 실질 점수와 거품을 학부모에게 보여줄 것인가?
   보여주면 설득력이 크지만, "찍어서 맞았다"는 표현은 민감할 수 있습니다.
4. **재응시** — 같은 시험을 다시 보면 새 기록인가, 기존 기록 갱신인가?
