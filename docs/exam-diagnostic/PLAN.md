# 시험 진단 입력 — 재설계 계획

> 작성: 2026-08-11 · 대상 화면 `src/features/ExamDiagnosticInput.js`
> 근거: 6축 병렬 감사 + 적대적 반증 (생존 80건 / 반증 6건, 치명 11 · 높음 24)

---

## 0. 지금 상태 요약

한 줄로: **이 화면은 채점에 쓸 수 없고, 저장된 데이터는 학생·학부모에게 도달하지 않습니다.**

세 겹의 문제가 겹쳐 있어 하나만 고쳐도 다음 것이 드러납니다.

```
① 입력 불가   반 학생 명단이 항상 비어 있음        → 채점 자체가 시작 안 됨
② 점수 오염   만점 100 고정 + 배점 0 폴백 실패     → 저장돼도 숫자가 틀림
③ 도달 실패   examDocId 미저장 + 이름으로 조회      → 맞아도 화면에 안 나옴
```

`examDocId` 를 고치는 순간 ②에서 잘못 쌓인 점수가 **한꺼번에 학부모에게 노출**됩니다.
그래서 순서가 중요합니다. ③을 먼저 고치면 안 됩니다.

## 2. 확정된 채점 방식 — 문항별 원점수 하나

### 결정 (2026-08-11, 원장)

| 항목 | 결정 |
|---|---|
| 점수 체계 | **원점수**. 개념테스트도 문항별 원점수를 따로 지정 |
| 입력 개수 | **하나**. 문항별 정오 표시에서 자동 산출 |
| `lucky`(찍맞) 판정 | **폐기** |
| 학부모 노출 고민 | `lucky` 폐기로 소멸 |
| 재응시 | **새 기록**. 보는 시점이 다르므로 갱신하지 않음 |

한때 표면 점수 / 실질 점수 두 가지를 두는 안을 검토했습니다.
찍어서 맞은 것을 걷어낸 점수가 실력을 더 정확히 보여주기 때문입니다.
폐기한 이유는 **판정 비용**입니다 — 문항마다 풀이를 읽어야 하고, 판정이 주관적이며,
검수 인력이 부족한 상황에서 지속되지 않습니다.

대신 **서술형 부분점수**가 같은 역할을 일부 대신합니다.
논리에 구멍이 있으면 부분점수로 깎이므로, 원점수 자체가 실력을 어느 정도 반영합니다.

```
만점  = Σ 문항 배점
점수  = 만점 − Σ 오답 문항의 배점
```

### 조교 권한

- Firestore 규칙: `STAFF()` 에 `ta` 가 이미 포함돼 있습니다 (`firestore.rules:83`). **변경 불필요.**
- 화면 라우트: `App.js:101,665` 가 조교를 막고 있었습니다. → **열었습니다.**
- 조교는 오답 문항 번호를 입력합니다. 코멘트·성장 플랜은 강사가 씁니다(화면 분리는 4단계).

## 3. 데이터 스키마 v2

```yaml
# artifacts/{APP_ID}/public/data/student_exam_diagnostics/{docId}
schemaVersion: 2

# ── 시험 식별 ──────────────────────────────────
kind: school | concept | mock
examDocId: "2026_목동고_2학년_1학기_중간고사_수학"   # school 일 때만. 나머지는 없음(정상)
examTitle: "[개념테스트] 7월 4주차 주간평가"          # 항상 있음. 화면 표시는 이걸로
unitName: "함수의 극한과 연속"
subject: "수학"

# ── 학생 ──────────────────────────────────────
studentId: "abc123"        # ← 유일한 조회 키. 이름으로 조회하지 않는다
studentName: "홍길동"       # 표시용 사본. 이름이 바뀌어도 기록은 안 끊긴다

# ── 채점 회차·반 (나중에 되살릴 수 없음) ─────────
batchId: "abc123"          # 같은 회차에 채점된 학생들을 묶는 값
classId / className        # 그때 어느 반으로 채점했는가
season                     # 그때의 시즌
gradedBy                   # 채점자

# ── 점수 (원점수) ──────────────────────────────
score: 64                  # 원점수
maxScore: 80               # 만점 = Σ 문항 배점. 100 고정 폐기

# ── 문항 구성의 지문 ───────────────────────────
questionCount: 25
questionSignature: "nkkv6i"   # 채점 이후 시험 마스터가 바뀌었는지 판정

# ── 문항별 (미래 분석의 씨앗) ────────────────────
responses:
  - no: "3"                # 시험지에 적힌 번호. 겹칠 수 있다
    qIndex: 2              # 마스터 questions[] 와 맞대는 유일하게 안전한 열쇠
    points: 4
    unitRaw: "이차함수"     # 채점 시점의 단원명 스냅샷
    verdict: correct       # correct | wrong
    errorType: null        # calc | condition | concept | time | blank

wrongQuestionNumbers: ["12"]   # 기존 소비자 호환용. responses 가 정본

instructorComment: ""
growthPlan: ""
createdAt / updatedAt
```

### 지금 안 넣지만 자리를 비워두는 것

`responses[]` 항목에 나중에 필드를 더해도 기존 기록은 그대로 동작합니다.

```yaml
  - no: "12"
    points: 5
    verdict: wrong
    # ↓ 2차 개발에서 추가. 없어도 지금 동작함
    conceptIds: ["ANA-07-03-05"]        # AI 수학 지식 맵 연결
    errorType: 계산실수 | 개념부재 | 문제해석 | 시간부족
    timeSpent: 210                       # 초
```

**이 `responses[]` 배열 하나가 미래 분석 전체의 전제조건입니다.**
지금 `wrongQuestionNumbers: ['3','7']` 만 저장하면 나중에 문항별 데이터를 붙일 자리가 없습니다.

## 4. 문항별 데이터로 열리는 것

`responses[]` 가 쌓이면 아래가 **추가 입력 없이** 계산됩니다.

| 분석 | 필요 조건 | 누구에게 쓸모 |
|---|---|---|
| 문항별 정답률 | 같은 `examDocId` 기록 여러 건 | 강사 — 다음 수업에서 다룰 문항 우선순위 |
| 거품률 순위 | `bubble / maxScore` | 원장 — 점수는 높은데 위험한 학생 조기 발견 |
| 오답 상위 문항 | `verdict == wrong` 집계 | 강사 — 반 전체 공통 취약점 |
| 찍맞 상위 문항 | `verdict == lucky` 집계 | 강사 — 학생들이 원리 없이 넘어간 문항 |
| 학생별 추이 | `studentId` + `createdAt` | 학부모 상담 — 실질 점수 추이가 진짜 성장 곡선 |
| 취약 개념 → 클리닉 과제 | `conceptIds` (2차) | 조교 — 클리닉 과제 자동 생성 |

### 집계는 클라이언트가 하지 않습니다

`exam_stats/{examDocId}` 집계 문서를 **Cloud Functions `onWrite`** 로 만듭니다.

- 클라이언트가 반 전체 기록을 읽으면 문서 읽기 비용이 학생 수만큼 곱해집니다
- 같은 계산식이 화면마다 복제되면 서로 다른 숫자가 나옵니다 (온톨로지에서 겪은 문제와 동일)

## 5. 작업 순서

각 단계는 앞 단계 없이는 검증할 수 없습니다.

| 단계 | 작업 | 상태 |
|---|---|---|
| **0** | 반 학생 명단을 `enrollments` 기준으로 복구 | ✅ 완료 |
| **1** | 원점수 채점 엔진 — `maxScore` 명시, 배점 0 폴백 수정, 문항 구성 변경 시 재계산 | ✅ 완료 |
| **2** | 탭·반 전환 시 입력 유실 확인창 | ✅ 완료 |
| **3** | 스키마 v2 저장 — `responses[]` · `examDocId` · `schemaVersion` | ✅ 완료 |
| **4** | 조교 라우트 개방 | ✅ 완료 |
| **5** | 규칙: 점수 상한을 `maxScore` 기준으로 (테스트 12건 추가) | ✅ 완료 |
| **6** | 기록 관리 화면 — 조회·수정·삭제 (`ExamDiagnosticRecords.js`) | ✅ 완료 |
| **7** | 소비자 화면 복구 — `studentId` 조회, 학부모 자녀 선택, `examDocId` 부재 허용 | ✅ 완료 |
| **8** | `concept_stats` 쓰기를 유니버스 읽기 모양에 맞춤 (고정값 70/B등급 제거) | ⬜ |
| **9** | `exam_stats` 집계 Functions + 문항별 분석 화면 | ⬜ |

**7단계를 6단계보다 먼저 하면 안 됩니다.** 잘못 저장된 기록을 고칠 수단 없이
학생·학부모 화면부터 열면, 되돌릴 방법이 없는 채로 노출됩니다.

### 7단계에서 정한 것

- 조회는 `where('studentId','==', ...)` **하나만** 겁니다. `orderBy` 를 함께 걸면
  복합 색인이 필요하고, 색인이 없으면 조회가 통째로 실패합니다. 정렬은 받아서 합니다.
- `examDocId` 가 **없는 것이 정상**입니다(개념테스트·모의고사). 있을 때만
  등급컷·난이도·총평을 덧붙이고, 없으면 저장된 `examTitle` 로 표시합니다.
- 추이 그래프는 **만점 대비 비율(%)** 로 그립니다. 시험마다 만점이 달라
  원점수를 그대로 이으면 오르내림이 뜻을 잃습니다. 원점수는 표에 그대로 둡니다.
- 오답 분석은 기록 자신의 `responses`(문항별 정오·배점)를 정본으로 씁니다.
  마스터의 `questions` 는 개념·난이도를 덧붙이는 데만 씁니다.

### 6단계에서 정한 것

- 화면은 새 메뉴가 아니라 **시험 진단 입력 안의 전환 탭**입니다(「채점 입력」/「저장된 기록·수정」).
- 조회는 `createdAt` 최신순 100건씩. 반·이름 필터는 **불러온 범위 안에서** 거릅니다.
  서버에서 좁히려면 복합 색인이 필요한데, 색인이 없으면 조회가 통째로 실패합니다.
- **삭제는 원장과 강사만** 할 수 있습니다(`firestore.rules:415`). 조교·데스크에게는
  버튼을 보여주지 않습니다 — 눌러도 거부될 뿐입니다.
- `schemaVersion` 이 2 가 아닌 기록에 **「재채점 필요」** 표시를 붙입니다.
  열어서 점수를 확인하고 저장하면 v2 로 올라가며 표시가 사라집니다.
- 문항 정보(`responses`)가 있는 기록은 문항을 눌러 정오를 바꾸면 점수가 다시 계산됩니다.
  만점은 배점 합계라 직접 고칠 수 없습니다.

**6단계를 1·3단계보다 먼저 하면 안 됩니다.** 지금 DB 에 쌓인 잘못된 100점들이
그 순간 학생·학부모 화면에 한꺼번에 드러납니다.

### 기존 데이터 처리

2026-07-23 이후 이 화면으로 저장된 기록은 `examDocId` 가 없고 점수가 100 고정일 수 있습니다.
6단계 전에 **점검 스크립트로 전수 조회 → 원장 확인 → 일괄 정정 또는 숨김** 이 필요합니다.
`schemaVersion` 이 없는 기록은 화면에서 "재채점 필요"로 표시하는 것이 가장 안전합니다.

## 5-1. 스키마 동결 (2026-08-11 완료)

컬렉션이 0건일 때만 공짜인 작업이라 먼저 했습니다.
**나중에 계산해 낼 수 없는 것**만 담는다는 기준으로 골랐습니다.

| 필드 | 왜 지금 담아야 하는가 |
|---|---|
| `batchId` | 같은 회차 채점 묶음. 반 평균·문항별 정답률의 단위. 사후 복원 불가 |
| `classId` / `className` / `season` | 학생이 반을 옮기면 '그때 어느 반이었나' 를 알 수 없다 |
| `qIndex` | 마스터 `questions[]` 와 맞대는 유일하게 안전한 열쇠. 번호는 겹치거나 바뀐다 |
| `unitRaw` | 채점 시점의 단원명. 마스터를 고치면 과거 기록의 단원이 사라진다 |
| `questionSignature` | 채점 이후 마스터가 수정됐는지 판정. 다르면 순번 대조를 믿으면 안 된다 |
| `errorType` | 자리를 안 만들면 이미 쌓인 기록에는 영영 못 채운다 |

`errorType` 이 가장 중요합니다. 지금 구조는 **'시간이 없어 못 푼 것' 과 '틀린 것' 을
둘 다 `wrong` 으로** 저장합니다. 시험지 뒷번호는 대개 어려운 문항이라,
**시간에 쫓긴 학생이 자동으로 '고난도 취약' 으로 진단됩니다.** 오판이 한쪽으로만 쏠립니다.

채점할 때는 비워 두고, 기록 관리 화면의 수정창에서 나중에 채웁니다.

## 6. 다음에 결정할 것

1. **서술형 부분점수** — 지금 문항은 정답/오답 둘 중 하나입니다.
   부분점수를 넣으려면 `responses[].earned` 를 더하고 문항 버튼을 숫자 입력으로 바꿉니다.
   스키마에 자리가 있어 기존 기록을 건드리지 않고 추가할 수 있습니다.
2. **7월 23일 이후 기록 처리** — `schemaVersion` 이 없는 기록은 점수가 틀렸을 수 있습니다.
   전수 조회 → 원장 확인 → 재채점 또는 숨김. **7단계 전에 끝내야 합니다.**
3. **조교와 강사의 화면 분리** — 지금은 조교도 코멘트·성장 플랜을 쓸 수 있습니다.
   조교에게는 채점만 보이게 할 것인지.
4. **재응시 구분** — 새 기록으로 쌓는 것은 확정. 다만 같은 시험이 여러 건일 때
   화면에서 "1차 / 재응시" 로 구분해 보여줄지는 7단계에서 정합니다.
